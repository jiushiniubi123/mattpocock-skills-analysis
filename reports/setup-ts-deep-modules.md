# setup-ts-deep-modules - 详细分析报告

## 📌 基本信息
- 分类：in-progress
- 技能定位：给 TypeScript 项目装上“门禁系统”，强制代码模块做到“对外极简、对内丰富”。
- 适用人群：中大型 TypeScript/Monorepo（多包仓库）项目的架构师、前端/Node.js 开发者。
- 使用难度：⭐⭐⭐（需要理解模块边界概念及配置工具）

## 🎯 它是干什么的
想象一家高级餐厅，顾客（外部代码）只能在菜单（入口文件）上点菜，绝对不能直接跑到后厨（子文件夹）去拿食材。这个技能就是帮你给代码库装上严格的“门禁系统”。

在编程中，我们常希望代码“对外看起来极其简单，但内部能处理很复杂的逻辑”（这叫深度模块）。这个技能利用一个叫 `dependency-cruiser` 的工具，强制规定：别人用你的代码，只能通过你公开的“大门”（根目录的入口文件）进，绝对不允许偷偷翻墙去用你内部的“小零件”（子文件夹里的实现）。它不仅能帮你配置好这套规则，还会故意“违规”一次来测试门禁是否真的管用。

## 🚀 使用场景
1. **大型多包仓库（Monorepo）治理**：项目里有几十个包，互相乱引用，导致“牵一发而动全身”。用它来理清边界，防止包与包之间“乱攀亲戚”。
2. **开发开源工具库**：你写了一个复杂的工具，希望给用户提供极简的 API。用它防止用户误用你内部未公开的接口，避免未来升级时用户代码崩溃。
3. **规范 AI 编程行为**：AI 写代码时为了图快，经常直接 import 你内部的深层文件。用它给 AI 戴上“紧箍咒”，强迫 AI 只通过正规入口调用代码。
4. **重构老旧“大杂烩”代码**：把以前那种把所有东西都塞在一个 `index.ts` 里导出的坏习惯，改造成清晰的“多个小入口、隐藏内部实现”的现代结构。

## 🔄 核心工作流程
这个技能的核心方法论是“深度模块设计”，它通过 7 个自动化步骤帮你落地：
1. **摸清家底**：自动检测你用的包管理器（npm/pnpm/yarn）和代码存放的根目录。
2. **请来保安**：自动安装 `dependency-cruiser` 这个依赖检查工具。
3. **制定门禁规则**：生成配置文件，确立四条铁律（只能从入口进、内部随便用、测试只能从入口进、禁止循环依赖）。
4. **接入日常巡检**：把门禁检查加入到项目的日常 lint（代码检查）流程中。
5. **打个样板**：自动创建一个标准的“示例包”，展示正确的目录结构。
6. **抓个典型（核心）**：故意写一段违规代码（比如从外部直接导入内部文件），看工具是否报错，证明规则真生效。
7. **广而告之**：自动写好说明文档，并在项目的 AI 指令文件（如 `CLAUDE.md`）中加上提示，让 AI 以后都遵守这个规矩。

## 🧪 实测/模拟记录
**背景**：假设我们有一个 `user-auth`（用户认证）包，原本它的 `index.ts` 像个垃圾桶，把内部的数据库查询函数 `queryUser` 也导出了。

**执行过程**：
1. 我让 AI 运行该技能。AI 迅速检测到我是 pnpm 环境，安装了 `dependency-cruiser`，并在根目录生成了 `.dependency-cruiser.cjs` 配置文件。
2. AI 开始重构目录：它把 `queryUser` 移到了 `user-auth/lib/db.ts` 中，并修改了 `index.ts`，只对外暴露 `login()` 和 `logout()` 两个干净的函数。
3. **最精彩的“破坏性测试”环节**：AI 为了证明规则生效，故意在 `tests/auth.test.ts` 里写了一行违规代码：`import { queryUser } from "../lib/db"`。
4. AI 运行 `lint:boundaries` 检查。终端立刻飘红，精准报出错误：`tests-through-entrypoints`（测试文件必须通过入口点导入）。
5. AI 看到报错后，心领神会地把代码改回 `import { login } from "../index"`，再次运行检查，终端显示全绿通过。
6. 最后，AI 在 `src/packages/README.md` 写好了规范，并在 `AGENTS.md` 里加了一句：“Packages are deep modules: see README before importing.”

**结果**：整个过程不到 2 分钟，不仅完成了代码结构重构，还确保这套规则在未来无论是人类还是 AI 写代码时，都不会被破坏。

## ✅ 优点
1. **治好了“代码乱伦”**：彻底杜绝了循环依赖和越权调用，让项目结构像外科手术一样干净。
2. **强迫“小接口、大实现”**：降低了使用者的心智负担，别人用你的代码再也不用看几百行的导出列表。
3. **自带“破坏性验证”**：很多配置工具配完就完了，这个技能会故意犯错来测试配置，确保“门禁”不是摆设。

## ⚠️ 局限性与注意事项
1. **历史包袱改造痛苦**：如果你的老项目一开始就是扁平结构，改造起来需要大量手动调整 import 路径。AI 能帮你配好规则，但填补违规代码的坑还得靠人。
2. **学习门槛**：非前端开发者理解“深度模块”和“桶文件（Barrel files）”等概念需要一定时间，团队推广时需要先对齐认知。

## 👥 适合谁用 / 不适合谁用
- **适合谁**：维护多包仓库的架构师、希望提升代码库质量的 TypeScript 开发者、被 AI 乱引内部文件搞崩溃的提示词工程师。
- **不适合谁**：写一次性脚本的人、单文件小项目、刚学 TypeScript 的新手（建议先学会写代码，再学架构设计）。
