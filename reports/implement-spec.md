# implement-spec - 详细分析报告

## 📌 基本信息
- 分类：in-progress
- 技能定位：基于需求规范和多线程子代理的自动化代码实现与合并引擎。
- 适用人群：需要处理复杂、大型需求，且希望 AI 能自动拆解、并发执行并最终合并代码的高级开发者或技术团队。
- 使用难度：⭐⭐⭐（需要理解任务图、子代理、独立工作区等概念，前期配置和准备要求较高）

## 🎯 它是干什么的
传统的 AI 写代码是“给个需求，写一段代码”，而 `implement-spec` 是让 AI 当“包工头”。它把大需求拆成很多小任务，并搞清楚谁必须先做、谁可以同时做。然后，它会派出多个“AI 小工”（子代理）在后台同时干活，干完一个就合并一个，最后统一检查质量，直接交给你一个完整的代码分支。简单来说，它就是一个能“多线程并发写代码并自动组装”的 AI 工程总指挥。

## 🚀 使用场景
1. **开发大型新功能**：比如要开发一个完整的“电商积分系统”，包含规则配置、积分计算、历史记录等。用它可以让多个 AI 同时开工，不用排队等。
2. **跨模块的系统重构**：需要同时修改数据库、后端接口和前端页面，且它们之间有严格的依赖关系时，用它来统筹全局。
3. **基于详细设计文档的批量开发**：当产品经理或架构师已经写好了非常详细的规范文档（Spec）和工单（Tickets）时，直接扔给它去全自动执行。

## 🔄 核心工作流程
这个技能的核心在于“统筹”与“并发”，具体步骤如下：
1. **读懂图纸（解析任务图）**：阅读需求规范和工单。它不把任务当成简单的流水账，而是画出一张“任务依赖图”，找出当前能立刻开工的任务（即“前沿任务”）。
2. **前期勘探（探索子代理）**：派一个 AI 去查阅现有代码库或外部文档，把调研笔记存好，让后面写代码的 AI 专心干活，不被杂事分心。
3. **建立工地（创建分支与 PR）**：创建一个专属的代码分支，并建立一个“草稿”状态的合并请求（Draft PR）。
4. **多线程施工（实现子代理）**：给每个能开工的小任务分配一个独立的“AI 小工”，它们在各自独立的代码工作区（worktree）里同时写代码，互不干扰。
5. **进度汇报与组装（合并子代理）**：一个小工干完活，就派另一个“合并小工”把代码合并到主分支上。
6. **动态调度**：主分支一变，原来被卡住的任务可能就能做了。系统会自动识别新解锁的任务，继续派出 AI 小工，保持最高效率。
7. **质量验收（代码审查）**：所有任务做完后，自动运行代码审查，发现 Bug 集中修复。
8. **交付与打扫**：把草稿 PR 标记为“可审查”状态，并清理所有临时工作区，保持环境整洁。

## 🧪 实测/模拟记录
**场景**：开发“购物车优惠券抵扣功能”。
**输入**：提供了一份包含 5 个工单的需求规范（1. 数据库加字段；2. 后端计算逻辑；3. 前端展示；4. 接口联调；5. 边界测试）。

**执行细节**：
- `implement-spec` 启动后，首先分析出工单 1（数据库）和工单 3（前端）没有依赖，可以并行。
- 它立刻派出 Agent A 和 Agent B。Agent A 在自己的独立工作区改数据库，Agent B 在另一个工作区写前端 UI。
- 10 分钟后，Agent A 先完成。合并子代理立刻将 Agent A 的代码合并到主分支。
- 此时，系统重新计算“任务图”，发现工单 2（后端计算）的前置条件已满足，立刻解锁。Agent C 被派出开始写后端逻辑。
- 最终，所有 5 个工单全部完成并合并。系统自动触发 `/code-review`，审查发现前端没处理“优惠券金额为 0”的极端情况。
- 系统自动派出一个修复子代理，用 1 分钟修复了该 Bug。
- 最终，一个干净、完整、经过审查的 PR 被标记为 Ready，整个过程无需人工干预代码合并。

## ✅ 优点
1. **极致并发，效率翻倍**：打破了传统 AI 串行写代码的瓶颈，多个子代理同时干活，大幅缩短开发时间。
2. **上下文隔离，减少“幻觉”**：每个小工在独立工作区干活，且通过“上下文指针”沟通，避免了 AI 因为上下文太长、信息太杂而“变笨”或写错代码。
3. **流程闭环，交付质量高**：自带勘探、合并、代码审查和自动修复流程，最终交付的是经过审查的完整代码，而不是需要人工擦屁股的半成品。

## ⚠️ 局限性与注意事项
1. **前期准备成本极高**：它严重依赖清晰、结构化的 Spec 和 Tickets。如果你的需求本身是一团乱麻，或者工单写得含糊不清，这个 Skill 也救不了，甚至会生成一堆垃圾代码。
2. **资源消耗巨大**：同时跑多个子代理和独立工作区，对本地机器的 CPU/内存，以及 API 的并发额度和 Token 消耗要求极高，容易“烧钱”。
3. **仍处于开发中（in-progress）**：作为未正式推广的技能，在复杂的边缘情况下可能存在 Bug，需要使用者有一定的排错和调试能力。

## 👥 适合谁用 / 不适合谁用
**适合谁用**：有完善需求文档的中大型项目开发者、喜欢折腾 AI 工作流的高级极客、需要批量处理复杂任务的架构师。
**不适合谁用**：需求模糊的“边想边写”型开发者、只写简单小脚本或几百行代码的新手、电脑性能较差或 API 额度有限的用户。

## 📊 综合评分
- **实用性：8/10**（对大型项目极具价值，能真正解决复杂工程的自动化问题，但对小项目属于杀鸡用牛刀）。
- **易用性：6/10**（概念较多，如任务图、worktree、子代理等，配置复杂，对新手和非程序员不太友好）。
- **创新性：9/10**（将任务依赖图、多代理并发、工作区隔离结合得非常巧妙，代表了 AI 编程从“单点辅助”向“工程统筹”演进的前沿理念）。
- **总分：7.5/10**
