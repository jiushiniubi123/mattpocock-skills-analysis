# to-spec - 详细分析报告

## 📌 基本信息
- 分类：engineering
- 技能定位：把和 AI 的聊天讨论转化为正式的开发“施工图纸”（规格说明书），并自动发布到任务管理系统。
- 适用人群：使用 AI 辅助编程的开发者、技术负责人、希望规范 AI 编码流程的工程师。
- 使用难度：⭐⭐（需要前期配置好任务管理工具，但使用本身很自然）

## 🎯 它是干什么的
简单来说，`to-spec` 就是一个“会议纪要转施工图纸”的工具。当你和 AI 激烈讨论完一个功能怎么做之后，它不需要你再重新描述一遍需求，而是直接总结你们刚才聊的内容，结合项目现有的代码情况，生成一份结构化的“规格说明书”（Spec）。这份说明书会详细列出要解决什么问题、用户故事有哪些、技术上怎么实现、怎么测试，最后自动帮你提交到 GitHub 等任务管理系统里。它的核心目的是让 AI 在写代码前“想清楚”，避免 AI 为了写代码而写代码，导致项目越来越乱。

## 🚀 使用场景
1. **需求讨论刚结束，准备动手开发**：你和 AI 通过对话把“用户登录模块”的需求、边界条件都盘清楚了，直接用它生成正式文档，防止 AI 后续写代码时“失忆”。
2. **接手复杂老项目，梳理新功能**：在老代码上加功能怕改坏？用它先梳理出现有代码结构，规划好要在哪里做测试，生成一份不改动老代码的“安全施工图纸”。
3. **团队协作，统一开发目标**：把 AI 生成的标准化 Spec 发给团队其他成员或另一个 AI 代理，大家看着同一份“图纸”干活，避免各写各的，减少沟通成本。

## 🔄 核心工作流程
`to-spec` 的工作流非常严谨，主要分为三步：
1. **勘察现场（探索代码库）**：AI 会先去翻看项目现有的代码，了解当前的架构和“行话”（领域词汇），并参考之前的架构决策，确保新方案不跟老规矩冲突。
2. **规划“测试接缝”（找准测试点）**：AI 会找出代码中适合插入测试的地方（接缝）。它尽量利用现有的测试点，少造新轮子。规划好后，会跟你确认：“老板，我打算在这几个地方加测试，您看行吗？”
3. **绘制图纸并归档（生成 Spec 并发布）**：AI 按照标准模板写出规格说明书。里面包含问题陈述、大量详细的用户故事、技术实现决策（只写核心逻辑，不写死具体代码文件）、测试策略和“不做什么”（明确边界）。写完后，自动发布到任务系统，并打上“准备好让 AI 施工”的标签。

## 🧪 实测/模拟记录
**场景**：我想给公司的内部打卡系统加一个“迟到自动补卡申请”功能。
**操作过程**：
1. 我先在终端里跟 AI 聊了半小时，讨论了补卡的规则（比如每月只能补2次）、审批流程等。
2. 聊完后，我输入 `/to-spec`。
3. AI 开始自动运行。它先花了几十秒扫描了我的项目代码，发现我们用的是 React 前端和 Node.js 后端，并且识别出了我们项目里叫 `AttendanceRecord` 的核心数据模型。
4. 接着，AI 向我确认：“我打算在 `AttendanceRecord` 的状态机里增加一个 `pending_makeup`（待补卡）状态，并在后端的 API 层增加一个校验接口，您看这两个测试接缝合适吗？”我回复：“合适，就这么干。”
5. 随后，AI 生成了一份长达两页的 Spec。里面不仅有“作为员工，我想申请补卡，以免被扣全勤奖”这种详细的用户故事，还在“实现决策”里明确了“补卡次数限制由后端 Redis 缓存控制，不查数据库”。
6. 最后，AI 自动在 GitHub 上创建了一个 Issue，标题是《Feat: 迟到自动补卡申请》，把 Spec 内容填了进去，并打上了 `ready-for-agent` 标签。整个过程一气呵成，我只需点个确认。

## ✅ 优点
1. **防止 AI “自由发挥”导致代码变烂**：AI 写代码很快，但容易把项目搞成一团乱麻。`to-spec` 强制 AI 在写代码前明确边界和架构，控制了“软件熵增”。
2. **极高的标准化与可读性**：生成的 Spec 模板非常科学，特别是“用户故事”和“超出范围”这两块，把需求卡得死死的，非技术人员也能看懂要做什么。
3. **无缝衔接自动化流程**：自动发布到任务系统并打上特定标签，可以直接作为下一步 AI 自动写代码（如配合 `/tdd` 或 `/implement`）的完美输入。

## ⚠️ 局限性与注意事项
1. **极度依赖前期的讨论质量**：`to-spec` 只是“总结”你们聊过的内容。如果你没跟 AI 讨论清楚就直接跑这个技能，它只能靠猜，生成的图纸会完全没法用。
2. **需要前置配置**：它需要项目提前配置好任务跟踪器（如 GitHub Issues）和特定的标签词汇（如 `ready-for-agent`）。如果是个人小项目没配置好，它会直接罢工并让你去跑 `/setup` 命令。

## 👥 适合谁用 / 不适合谁用
**适合谁用**：注重代码质量、希望用 AI 规范开发流程的工程师；使用 AI 代理进行复杂项目开发的团队；需要把模糊想法转化为清晰任务的管理者。
**不适合谁用**：只想让 AI 随便写个脚本、不在乎代码结构的“随手党”；没有使用 GitHub/Linear 等任务管理系统，习惯在本地记事本里记需求的个人开发者。

## 📊 综合评分
- 实用性：9/10（完美解决了 AI 编码“想不清就动手”的痛点，是工程化落地的关键一环）
- 易用性：8/10（触发简单，但首次使用需要配置环境，且需要用户具备一定的架构确认能力）
- 创新性：8/10（将传统的软件工程“需求分析”与 AI 提示词工程巧妙结合，用 Spec 驱动 AI 而非让 AI 盲目生成）
- 总分：8.5/10（一款能让 AI 从“代码生成器”进化为“正规军”的优秀工程技能）
